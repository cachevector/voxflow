VOXFLOW PROJECT SPEC
Cross-platform AI dictation for macOS and Windows, built on Rust + Tauri + React
Updated: 2026-07-16

============================================================
0. PRODUCT IDENTITY
============================================================

Product name: VoxFlow
Domain: voxflow.maskedsyntax.com
Category: AI dictation / OS-level writing layer / BYOK voice input
Primary platform: macOS
Secondary platform: Windows 11
Core idea: A small, native-feeling voice bar that appears only when needed, listens instantly, transcribes quickly, rewrites speech into a polished sentence, and inserts text into the current app without interrupting the user's flow.

One-line positioning:
VoxFlow is a fast, BYOK voice input layer for your desktop with a built-in AI rewrite pass.

Sharper positioning:
Speak anywhere. VoxFlow turns your voice into clean, well-formed text inside the app you are already using.

Developer-focused positioning:
An AI keyboard for macOS and Windows, built on Tauri + React. Dictate, rewrite, command, and paste across any app.

Primary business angle:
Not another AI subscription. VoxFlow is BYOK-first (including fully self-hosted setups), local-history-first, and built for people who care about speed, privacy, and control over their own cost.

============================================================
1. DOMAIN DECISION: voxflow.maskedsyntax.com
============================================================

Decision: Use voxflow.maskedsyntax.com for now.

This is the right decision for the current stage.

Why it is right:
- No new domain cost.
- Faster to launch.
- Keeps the product under your existing MaskedSyntax brand.
- Good enough for waitlist, beta, early users, demos, and social launches.
- You can validate demand before spending money on branding.
- It lets you ship multiple indie products under the same parent studio.

Potential downside:
- A subdomain can feel slightly less serious than a dedicated .app/.com domain once the product starts making money.
- If VoxFlow becomes your flagship app, a dedicated domain will look cleaner for SEO, press, ads, and long-term trust.

Recommended path:
Phase 1: Use voxflow.maskedsyntax.com for MVP, waitlist, beta, and early paid users.
Phase 2: If VoxFlow reaches 50-100 active users or $500+/month revenue, consider buying voxflow.app, getvoxflow.com, voxflow.ai, or voxflow.dev if available.
Phase 3: Keep voxflow.maskedsyntax.com as a redirect even if you buy a dedicated domain.

Verdict:
Use the subdomain now. Do not let domain buying slow the product down. The product experience matters much more than the domain at this stage.

3. PRODUCT PHILOSOPHY
============================================================

VoxFlow should feel like an OS feature, not like another productivity app.

Rules:
- Never steal focus unless necessary.
- Never open a large window during dictation.
- Never make the user copy/paste manually unless insertion fails.
- Never show too much UI while recording.
- Never block the current app with a modal unless permission is required.
- Always prioritize perceived speed.
- Always give a fallback path.
- Always make the user feel in control.

Core values:
- Fast enough to trust.
- Native enough to blend in.
- Cheap enough to use daily.
- Private enough to recommend.
- Calm enough to avoid interrupting flow.

============================================================
4. PRIMARY USER EXPERIENCE
============================================================

Ideal flow:
1. User places cursor in any text field.
2. User presses and holds global hotkey.
3. VoxFlow's small rounded bar appears at the bottom of the screen.
4. Recording starts immediately.
5. User speaks naturally.
6. User releases hotkey.
7. VoxFlow instantly finalizes audio.
8. Local VAD trims silence.
9. Transcription starts.
10. Optional cleanup rewrites the result.
11. Final text is inserted into the active app.
12. Bar disappears.

The interaction should feel like:
Press -> speak -> release -> text appears.

Target perceived latency:
- Bar appears: under 80 ms.
- Recording starts: under 100 ms.
- End-of-speech detection: under 250 ms after release.
- First transcription result for short speech: under 800 ms when possible.
- Final text insertion: ideally under 1.5 seconds for short snippets.
- For longer speech: show progress but avoid feeling stuck.

============================================================
5. PERFORMANCE IS THE PRODUCT
============================================================

VoxFlow cannot win if it is only cheaper. It must feel faster, calmer, and more reliable.

Performance principles:
- Keep the app resident in memory.
- Preload the selected local model after launch.
- Keep audio pipeline warm after first use.
- Use push-to-talk first because it avoids expensive always-listening complexity.
- Use VAD to avoid sending silence to cloud APIs.
- Stream or chunk intelligently depending on provider.
- Cache permission status and active app context.
- Avoid heavy UI rendering during recording.
- Use native/global APIs for hotkeys and text insertion instead of slow automation where possible.
- Never wait for rewrite if plain transcription is already good enough.

Performance budget:
- Idle CPU: below 1-2% on normal desktop machines.
- Recording CPU: below 5-8% for capture + VAD.
- Local transcription CPU/GPU: depends on model, but must not freeze UI.
- Memory: keep MVP under 300-500 MB with small local model loaded.
- Battery: provide battery saver mode on laptops.

Important UX detail:
Show progress in a tiny calm way. The user should always know whether VoxFlow is listening, processing, inserting, or done.

Recommended state labels:
- Listening
- Cleaning
- Inserting
- Copied
- Done

Avoid scary labels like:
- Uploading
- Waiting for API
- Processing request

============================================================
6. LATENCY ARCHITECTURE
============================================================

Pipeline:

Hotkey trigger
-> Wake audio session
-> Capture PCM audio
-> VAD trims silence
-> Noise suppression / gain normalization
-> Segment audio
-> Transcription route decision
-> Transcribe
-> Optional cleanup
-> Insert text
-> Store history locally

Key optimizations:

1. Pre-warm microphone
Do not initialize microphone from zero every time. Ask permission once, then keep a lightweight audio capture path ready.

2. Use VAD before transcription
Use WebRTC VAD, Silero VAD, or a lightweight Rust-compatible VAD. This reduces cost and latency by cutting silence.

3. Use short utterance mode
Most dictation is 2-15 seconds. Optimize for this case first.

4. Use local fallback instantly
For very short commands like "thanks", "yes", "ship it", local tiny/base model can be enough.

5. Separate transcription from cleanup
Do not run AI cleanup on every utterance by default. Use cheap cleanup rules first.

6. Insert immediately when confidence is high
If transcript is simple and high confidence, insert without cloud rewrite.

7. Parallelize cautiously
For cloud mode, upload compressed audio while final local VAD boundary is being computed if streaming is supported.

8. Model routing
Use different models for different cases:
- Short casual phrase: local small model or gpt-4o-mini-transcribe.
- Long professional text: gpt-4o-mini-transcribe + cheap text cleanup.
- High-accuracy mode: gpt-4o-transcribe.
- Offline mode: whisper.cpp / faster-whisper local.

============================================================
7. COST ARCHITECTURE
============================================================

Goal:
For BYOK users, keep normal usage under Rs.400/month and ideally under Rs.150-250/month.

OpenAI transcription reference:
- gpt-4o-mini-transcribe: $0.003/minute.
- gpt-4o-transcribe: $0.006/minute.

Approximate INR calculation using Rs.83-$1 for planning:
- $0.003/minute = about Rs.0.25/minute.
- $0.006/minute = about Rs.0.50/minute.

Usage scenarios with gpt-4o-mini-transcribe:

10 min/day x 30 days = 300 min/month
Cost: $0.90/month = about Rs.75/month

20 min/day x 30 days = 600 min/month
Cost: $1.80/month = about Rs.150/month

30 min/day x 30 days = 900 min/month
Cost: $2.70/month = about Rs.225/month

45 min/day x 30 days = 1350 min/month
Cost: $4.05/month = about Rs.336/month

60 min/day x 30 days = 1800 min/month
Cost: $5.40/month = about Rs.448/month

Conclusion:
If the user dictates under 45 minutes/day using gpt-4o-mini-transcribe, the cost can stay under around Rs.400/month. If they dictate around 1 hour/day, it can exceed Rs.400/month.

How VoxFlow keeps costs down:

1. VAD silence trimming
Do not bill silence.

2. Push-to-talk first
Avoid accidental background recording.

3. Local-first routing
Use local model for short/simple phrases.

4. API only when needed
Cloud is used for harder audio, noisy input, long text, or high-accuracy mode.

5. No automatic rewrite by default
AI rewrite can cost extra tokens. Use it only in selected modes.

6. User cost dashboard
Show estimated monthly cost based on minutes used.

7. Provider choice
Support any OpenAI-API-compatible endpoint through one generic adapter: OpenAI and Groq out of the box, plus a "Custom Endpoint" option (base URL + optional key) that works identically for a self-hosted server. A user running whisper.cpp-server/faster-whisper-server and llama.cpp-server/Ollama on their own hardware (e.g. a Raspberry Pi reachable over Tailscale) can point both the transcription call and the rewrite call at it and drive marginal API cost to roughly $0 — the only cost is the hardware and electricity they already own.

8. Quality modes
- Economy: cheapest configured model (mini-tier) only.
- Balanced: mini-tier transcription + AI rewrite pass.
- Accurate: highest-accuracy configured model.
- Custom Endpoint: self-hosted server (e.g. Raspberry Pi over Tailscale) — near-zero marginal cost, latency depends on the hardware.

9. Max session cap
Optional setting: stop recording after 60/120/300 seconds to prevent accidental cost.

10. Auto-detect silence
Stop recording after long silence if toggle mode is enabled.

Cost positioning:
VoxFlow should not promise that BYOK always costs less than Wispr Flow. Instead say:
"With BYOK, light-to-moderate users can often run VoxFlow for less than a typical dictation subscription. Heavy users can choose local mode or set monthly caps."

8. RECOMMENDED MVP COST MODES
============================================================

Mode 1: Custom Endpoint (Self-Hosted)
Cost: ~Rs.0/month marginal (hardware/electricity you already own)
Best for: privacy, a home server (e.g. Raspberry Pi over Tailscale) running an OpenAI-compatible transcription/rewrite server, experimentation
Downside: latency and accuracy depend entirely on the hardware you host it on

Mode 2: BYOK Economy
Provider: OpenAI gpt-4o-mini-transcribe
Cost: approx Rs.75-225/month for 10-30 min/day
Best for: daily use under Rs.400/month

Mode 3: BYOK Hybrid
Provider: cheap/mini model first, higher-accuracy model only when the router decides it's needed (long/noisy audio)
Cost: approx Rs.50-180/month for many users
Best for: VoxFlow's default recommended mode

Mode 4: Hosted Pro Later
VoxFlow manages provider keys and charges subscription
Cost to user: $5-$8/month target
Best for: non-technical users
Do not build this first.

MVP default:
BYOK Hybrid, with Custom Endpoint available as a first-class alternative from day one (not a later add-on).

11. PLATFORM-NATIVE PLAN
============================================================

Shared core:
Use Rust for the core audio pipeline, provider routing, hotkey abstraction, settings, secret storage, cost tracking, and local history — unchanged in spirit from the original plan.

UI strategy:
One shell for both platforms: Tauri v2 (Rust host) + React (TypeScript) frontend, for BOTH the settings/configuration window and the floating waveform bar. This is the primary plan, not a fallback — a single web-based UI layer kept small, fast, and carefully styled can match native feel closely enough when the hot path (hotkey capture, audio, state transitions) stays in Rust and only rendering lives in React. Two Tauri windows: a normal decorated settings window, and a small transparent/always-on-top/undecorated overlay window for the pill bar, shown/hidden imperatively from Rust so it can appear well within the latency budget without waiting on a JS round-trip.

macOS:
Shell: Tauri v2 window + React, packaged as a standard .app/.dmg via Tauri's bundler.
Core: Rust, linked directly into the Tauri binary (no FFI layer needed — Tauri commands/events replace what UniFFI-to-Swift would have done).

macOS permissions likely needed:
- Microphone: required for recording.
- Accessibility: required for reliable direct text insertion (AXUIElement API) and active app interaction.
- Input Monitoring: only needed if the hotkey implementation uses a raw CGEventTap (true for a bare-modifier-only binding like Left Control alone). A modifier+key combo hotkey avoids this requirement via tauri-plugin-global-shortcut; keep bare-modifier as an advanced opt-in.
- Automation: may be needed if controlling other apps via Apple Events.
- Screen Recording: avoid for MVP unless reading screen context later.

macOS native-feeling features (delivered via Tauri, not native Swift):
- Menu bar / tray icon (Tauri tray API).
- Floating overlay window styled as a rounded pill (transparent, undecorated, always-on-top).
- Subtle blur/vibrancy via CSS backdrop-filter, kept restrained per the visual style rules below.
- Launch at login (tauri-plugin-autostart).
- Permission onboarding checklist (React view + Rust permission-check commands).
- Settings window in React.
- Global hotkeys (tauri-plugin-global-shortcut, with a custom CGEventTap module for bare-modifier mode).
- Secure Keychain storage for API keys via the `keyring` crate (Rust), not plaintext JSON.

Windows:
Shell: the same Tauri v2 window + React, packaged as .msi/NSIS via Tauri's bundler.
Core: Rust, same binary/crate structure as macOS — no separate WinUI3 shell.
Audio: WASAPI (via CPAL, unchanged).
Text insertion: UI Automation first, clipboard + SendInput(Ctrl+V) fallback — treated as the primary reliable path on Windows day one since UIA tree coverage varies by target app.
Hotkey: tauri-plugin-global-shortcut (wraps RegisterHotKey-equivalent registration), with a raw low-level keyboard hook (SetWindowsHookExW) as the advanced bare-modifier option, mirroring the macOS CGEventTap path.
Storage: Windows Credential Manager via the same `keyring` crate used on macOS.
Native-feeling features:
- System tray icon + menu.
- Compact floating overlay window (same component as macOS, styled consistently).
- Startup task (tauri-plugin-autostart).
- Windows toast notification for permission/errors (tauri-plugin-notification).

Distribution note (both platforms):
Even with a web-based UI layer, shipped binaries still need OS-level trust: macOS needs a Developer ID signature + notarization to avoid Gatekeeper blocking the app, and Windows needs an Authenticode signature to avoid SmartScreen friction. Unsigned dev builds are fine for personal use during development; budget for these before any wider distribution.

13. TEXT INSERTION STRATEGY
============================================================

Insertion is one of the hardest parts.

Priority order:
1. Direct text insertion via accessibility/UI automation where safe.
2. Clipboard paste with clipboard restore.
3. Copy result and show "Copied" state if paste fails.
4. Manual paste fallback.

Clipboard restore behavior:
- Save previous clipboard.
- Place transcript on clipboard.
- Simulate paste.
- Restore previous clipboard after short delay if safe.
- Provide setting to disable clipboard restore.

Safety:
- In terminal apps, never auto-press Enter.
- For command-like text, insert only, do not execute.
- Allow blocklist apps where VoxFlow should not insert.

22. RISKS
============================================================

Biggest risks:
1. Latency feels worse than Wispr Flow, especially with a web-based UI layer.
2. Text insertion is unreliable across apps.
3. A self-hosted Custom Endpoint (e.g. a Raspberry Pi) is too slow or unreachable while traveling.
4. BYOK setup scares non-technical users.
5. Permissions on macOS feel intimidating.
6. Cloud cost exceeds user expectation.
7. Unsigned builds trigger Gatekeeper/SmartScreen friction during personal/beta use.

Mitigations:
1. Keep the hot path (hotkey, audio, state machine) in Rust; React only renders. Optimize short dictation path first.
2. Build fallback insertion paths.
3. Default to a cloud provider, with Custom Endpoint as an explicit opt-in that falls back gracefully on failure.
4. Make BYOK onboarding visual and simple.
5. Build a permission checklist screen.
6. Add spend caps and projections.
7. Document the "click More info -> Run anyway" workaround until certs are budgeted for.
