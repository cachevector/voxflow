1. DOMAIN DECISION: voxflow.maskedsyntax.com
============================================================

Decision: Use voxflow.maskedsyntax.com for now.

This is the right decision for the current stage.

Why it is right:
- No new domain cost.
- Faster to launch.
- Keeps the product under your existing MaskedSyntax brand.
- Good enough for waitlist, beta, early users, demos, and social launches.
- You can validate demand before spending money on branding.
- It lets you ship multiple indie products under the same parent studio.

Potential downside:
- A subdomain can feel slightly less serious than a dedicated .app/.com domain once the product starts making money.
- If VoxFlow becomes your flagship app, a dedicated domain will look cleaner for SEO, press, ads, and long-term trust.

Recommended path:
Phase 1: Use voxflow.maskedsyntax.com for MVP, waitlist, beta, and early paid users.
Phase 2: If VoxFlow reaches 50-100 active users or $500+/month revenue, consider buying voxflow.app, getvoxflow.com, voxflow.ai, or voxflow.dev if available.
Phase 3: Keep voxflow.maskedsyntax.com as a redirect even if you buy a dedicated domain.

Verdict:
Use the subdomain now. Do not let domain buying slow the product down. The product experience matters much more than the domain at this stage.

4. PRIMARY USER EXPERIENCE
============================================================

Ideal flow:
1. User places cursor in any text field.
2. User presses and holds global hotkey.
3. VoxFlow's small rounded bar appears at the bottom of the screen.
4. Recording starts immediately.
5. User speaks naturally.
6. User releases hotkey.
7. VoxFlow instantly finalizes audio.
8. Local VAD trims silence.
9. Transcription starts.
10. Optional cleanup rewrites the result.
11. Final text is inserted into the active app.
12. Bar disappears.

The interaction should feel like:
Press -> speak -> release -> text appears.

Target perceived latency:
- Bar appears: under 80 ms.
- Recording starts: under 100 ms.
- End-of-speech detection: under 250 ms after release.
- First transcription result for short speech: under 800 ms when possible.
- Final text insertion: ideally under 1.5 seconds for short snippets.
- For longer speech: show progress but avoid feeling stuck.

============================================================
5. PERFORMANCE IS THE PRODUCT
============================================================

VoxFlow cannot win if it is only cheaper. It must feel faster, calmer, and more reliable.

Performance principles:
- Keep the app resident in memory.
- Preload the selected local model after launch.
- Keep audio pipeline warm after first use.
- Use push-to-talk first because it avoids expensive always-listening complexity.
- Use VAD to avoid sending silence to cloud APIs.
- Stream or chunk intelligently depending on provider.
- Cache permission status and active app context.
- Avoid heavy UI rendering during recording.
- Use native/global APIs for hotkeys and text insertion instead of slow automation where possible.
- Never wait for rewrite if plain transcription is already good enough.

Performance budget:
- Idle CPU: below 1-2% on normal desktop machines.
- Recording CPU: below 5-8% for capture + VAD.
- Local transcription CPU/GPU: depends on model, but must not freeze UI.
- Memory: keep MVP under 300-500 MB with small local model loaded.
- Battery: provide battery saver mode on laptops.

Important UX detail:
Show progress in a tiny calm way. The user should always know whether VoxFlow is listening, processing, inserting, or done.

Recommended state labels:
- Listening
- Cleaning
- Inserting
- Copied
- Done

Avoid scary labels like:
- Uploading
- Waiting for API
- Processing request

============================================================
6. LATENCY ARCHITECTURE
============================================================

Pipeline:

Hotkey trigger
-> Wake audio session
-> Capture PCM audio
-> VAD trims silence
-> Noise suppression / gain normalization
-> Segment audio
-> Transcription route decision
-> Transcribe
-> Optional cleanup
-> Insert text
-> Store history locally

Key optimizations:

1. Pre-warm microphone
Do not initialize microphone from zero every time. Ask permission once, then keep a lightweight audio capture path ready.

2. Use VAD before transcription
Use WebRTC VAD, Silero VAD, or a lightweight Rust-compatible VAD. This reduces cost and latency by cutting silence.

3. Use short utterance mode
Most dictation is 2-15 seconds. Optimize for this case first.

4. Use local fallback instantly
For very short commands like "thanks", "yes", "ship it", local tiny/base model can be enough.

5. Separate transcription from cleanup
Do not run AI cleanup on every utterance by default. Use cheap cleanup rules first.

6. Insert immediately when confidence is high
If transcript is simple and high confidence, insert without cloud rewrite.

7. Parallelize cautiously
For cloud mode, upload compressed audio while final local VAD boundary is being computed if streaming is supported.

8. Model routing
Use different models for different cases:
- Short casual phrase: local small model or gpt-4o-mini-transcribe.
- Long professional text: gpt-4o-mini-transcribe + cheap text cleanup.
- High-accuracy mode: gpt-4o-transcribe.
- Offline mode: whisper.cpp / faster-whisper local.

7. COST ARCHITECTURE
============================================================

Goal:
For BYOK users, keep normal usage under Rs.400/month and ideally under Rs.150-250/month.

OpenAI transcription reference:
- gpt-4o-mini-transcribe: $0.003/minute.
- gpt-4o-transcribe: $0.006/minute.

Approximate INR calculation using Rs.83-$1 for planning:
- $0.003/minute = about Rs.0.25/minute.
- $0.006/minute = about Rs.0.50/minute.

Usage scenarios with gpt-4o-mini-transcribe:

10 min/day x 30 days = 300 min/month
Cost: $0.90/month = about Rs.75/month

20 min/day x 30 days = 600 min/month
Cost: $1.80/month = about Rs.150/month

30 min/day x 30 days = 900 min/month
Cost: $2.70/month = about Rs.225/month

45 min/day x 30 days = 1350 min/month
Cost: $4.05/month = about Rs.336/month

60 min/day x 30 days = 1800 min/month
Cost: $5.40/month = about Rs.448/month

Conclusion:
If the user dictates under 45 minutes/day using gpt-4o-mini-transcribe, the cost can stay under around Rs.400/month. If they dictate around 1 hour/day, it can exceed Rs.400/month.

How VoxFlow keeps costs down:

1. VAD silence trimming
Do not bill silence.

2. Push-to-talk first
Avoid accidental background recording.

3. Local-first routing
Use local model for short/simple phrases.

4. API only when needed
Cloud is used for harder audio, noisy input, long text, or high-accuracy mode.

5. No automatic rewrite by default
AI rewrite can cost extra tokens. Use it only in selected modes.

6. User cost dashboard
Show estimated monthly cost based on minutes used.

7. Provider choice
Support OpenAI first, then optionally Groq, Deepgram, AssemblyAI, Gemini, OpenRouter, and local Whisper.

8. Quality modes
- Economy: local + gpt-4o-mini only.
- Balanced: gpt-4o-mini + cleanup.
- Accurate: gpt-4o-transcribe.
- Offline: local only.

9. Max session cap
Optional setting: stop recording after 60/120/300 seconds to prevent accidental cost.

10. Auto-detect silence
Stop recording after long silence if toggle mode is enabled.

Cost positioning:
VoxFlow should not promise that BYOK always costs less than Wispr Flow. Instead say:
"With BYOK, light-to-moderate users can often run VoxFlow for less than a typical dictation subscription. Heavy users can choose local mode or set monthly caps."

11. PLATFORM-NATIVE PLAN
============================================================

Shared core:
Use Rust for core audio pipeline, provider routing, hotkey abstraction, settings, encryption, cost tracking, and local history.

UI strategy:
Use platform-specific UI shells where possible, backed by shared Rust core.

macOS primary:
Recommended UI: Swift / SwiftUI + AppKit helper layer.
Core: Rust via FFI or local service.
Why: best native feel, fastest permission/system integration, best menubar/floating panel support.

macOS permissions likely needed:
- Microphone: required for recording.
- Accessibility: likely required for reliable text insertion and active app interaction.
- Input Monitoring: may be needed depending on global hotkey implementation.
- Automation: may be needed if controlling other apps via Apple Events.
- Screen Recording: avoid for MVP unless reading screen context later.

macOS native features:
- Menu bar app.
- Floating NSPanel.
- Rounded bottom pill.
- Native vibrancy/blur carefully, not too shiny.
- Launch at login.
- Permission onboarding checklist.
- Settings window using SwiftUI.
- Global hotkeys.
- Secure keychain for API keys.

Linux COSMIC:
Recommended UI: Rust + libcosmic.
Audio: PipeWire.
Text insertion: Wayland-compatible approaches, with fallbacks.
Hotkeys: COSMIC/desktop portal support if available; otherwise document setup.
Storage: Secret Service / keyring for API keys.

Linux challenges:
- Wayland makes global hotkeys and text injection harder than X11.
- COSMIC is new and APIs may evolve.
- Text insertion may need clipboard fallback first.

Linux strategy:
- Build a great COSMIC-native app first.
- Use clipboard paste as reliable fallback.
- Support X11 later if feasible.
- Be transparent about Wayland limitations.

Windows:
Recommended UI: WinUI 3 or native Windows App SDK shell.
Core: Rust shared core.
Audio: WASAPI.
Text insertion: UI Automation / SendInput fallback.
Hotkey: RegisterHotKey.
Storage: Windows Credential Manager.
Native features:
- System tray.
- Compact floating bar.
- Startup task.
- Windows notification for permission/errors.

Cross-platform fallback:
If native shells slow development too much, use Tauri only for settings/dashboard, but keep the dictation bar as native as possible. Avoid making the main experience feel like a web app.

13. TEXT INSERTION STRATEGY
============================================================

Insertion is one of the hardest parts.

Priority order:
1. Direct text insertion via accessibility/UI automation where safe.
2. Clipboard paste with clipboard restore.
3. Copy result and show "Copied" state if paste fails.
4. Manual paste fallback.

Clipboard restore behavior:
- Save previous clipboard.
- Place transcript on clipboard.
- Simulate paste.
- Restore previous clipboard after short delay if safe.
- Provide setting to disable clipboard restore.

Safety:
- In terminal apps, never auto-press Enter.
- For command-like text, insert only, do not execute.
- Allow blocklist apps where VoxFlow should not insert.

22. RISKS
============================================================

Biggest risks:
1. Latency feels worse than Wispr Flow.
2. Text insertion is unreliable across apps.
3. Linux Wayland limitations create friction.
4. Local models are too slow on weak hardware.
5. BYOK setup scares non-technical users.
6. Permissions on macOS feel intimidating.
7. Cloud cost exceeds user expectation.

Mitigations:
1. Optimize short dictation path first.
2. Build fallback insertion paths.
3. Start with COSMIC and clipboard fallback.
4. Offer cloud mode as default for speed.
5. Make BYOK onboarding visual and simple.
6. Build a permission checklist screen.
7. Add spend caps and projections.
