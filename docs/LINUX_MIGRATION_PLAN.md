# VoxFlow Platform Swap: Windows → Linux (Wayland-first, X11 secondary)

> **Status: approved, not yet executed.** This is a planning document only — none of the changes described below have been made to the code yet. It's committed here so the swap can be picked up and executed from any machine, including one that isn't this one.

## Context

The VoxFlow rewrite (Rust + Tauri v2 + React, BYOK, generic OpenAI-compatible provider adapter — see `docs/REWRITE_PLAN.md`) was already planned and Phase 0 was implemented and verified, originally targeting **Windows + macOS**. The user now wants to drop Windows entirely and target **Linux + macOS** instead, with Linux prioritizing **Wayland** (the modern default on GNOME/KDE/most distros) and treating **X11 as the secondary/fallback** path.

This is not a pure find-and-replace. No Windows-specific Rust code was ever written yet (Phase 1's real Accessibility/UI-Automation insertion work hadn't started — the only OS-conditional code today is `crates/voxflow-insert/src/clipboard_paste.rs`'s `#[cfg(not(target_os = "macos"))]` branch, which already generalizes to Linux with zero changes needed). So most of this swap is mechanical (docs, spec, CI, packaging config). But the hotkey mechanism, text-insertion mechanism, and the floating overlay window's positioning behavior all relied on Windows-native APIs that have **no Wayland equivalent** — Wayland's security model deliberately blocks the things those relied on (global key grabbing, synthetic input, arbitrary window positioning), and the previous X11-based Linux prototype (deleted during the earlier rewrite) already ran into exactly this and settled on an honest "clipboard + manual paste" fallback for Wayland. This plan carries that same honesty forward rather than assuming things will "just work."

## What's genuinely different (not just renaming)

1. **Global hotkey.** `tauri-plugin-global-shortcut` (built on the `global-hotkey` crate) registers hotkeys via X11's `XGrabKey` on Linux — this does **not** work on pure Wayland. For Wayland-first support, the primary mechanism becomes the XDG Desktop Portal's `org.freedesktop.portal.GlobalShortcuts` interface, called over D-Bus (the `zbus` crate is the standard Rust client for this). The portal shows a one-time system binding dialog and emits `Activated`/`Deactivated` D-Bus signals, which map onto our existing press/release semantics. Support: GNOME 43+, KDE Plasma 6+, wlroots compositors with `xdg-desktop-portal-wlr` (Sway, Hyprland). Where the portal isn't available (older DEs, minimal WM setups, or an X11/XWayland session), fall back to `tauri-plugin-global-shortcut`'s existing X11 path as the secondary mechanism.
2. **Text insertion.** Wayland blocks arbitrary synthetic input system-wide by design. Primary Wayland path: the XDG Desktop Portal's `org.freedesktop.portal.RemoteDesktop` interface (also via `zbus`) can synthesize a paste keystroke, but requires one-time per-session user consent. When that's unavailable or denied, fall back to clipboard-copy-only with a "Copied — paste manually" overlay state — no synthetic input needed, always works. The existing `ClipboardPasteInserter` (arboard + enigo, already OS-generic via `#[cfg(not(target_os = "macos"))]`) becomes the X11-secondary path unchanged — enigo's XTest-based synthetic Ctrl+V already works correctly there.
3. **Floating overlay window.** The pill needs to be transparent, always-on-top, and pinned to a screen position — on Linux that's the `wlr-layer-shell` Wayland protocol, supported by wlroots compositors (Sway, Hyprland) and KDE Plasma, but **not supported by GNOME at all** (deliberate Mutter/GNOME policy). Tauri's Linux window backend (`tao`/GTK) does not give you layer-shell out of the box — this needs an early spike (Phase 1, before building further on top of it) to confirm it's achievable at all, likely via a separate GTK layer-shell binding. On GNOME Wayland, the honest fallback is a best-effort normal window (not reliably pinned/always-on-top) — document this limitation rather than promise parity with macOS.
4. **Secrets.** The `keyring` crate talks to the Secret Service D-Bus API (GNOME Keyring / KWallet) on Linux — present by default on GNOME/KDE sessions (the primary target), less certain on minimal/tiling-WM-only setups. Worth a doc note, not a blocker.
5. **No material change needed:** autostart (XDG `.desktop` entry), clipboard-manager, notifications (libnotify), window positioner — these already work across X11/Wayland via existing Tauri plugins and XDG conventions.

## New Rust work (Phase 1, real implementation — not mechanical)

- A Linux-specific hotkey module using `zbus` to call the `GlobalShortcuts` portal as primary, falling back to the existing `tauri-plugin-global-shortcut` X11 path when the portal isn't available — mirrors the graceful-fallback philosophy already used for the Windows hotkey-conflict case found in Phase 0 testing (log a warning, don't crash).
- A Linux-specific insertion enhancement using `zbus` to call the `RemoteDesktop` portal for synthetic paste, layered in front of the existing `ClipboardPasteInserter`'s copy-only fallback (which already works today, unchanged).
- An early spike task to validate whether Tauri's overlay window can achieve transparent/always-on-top/positioned behavior via `wlr-layer-shell` on a real wlroots or KDE Plasma Wayland session, before assuming the existing `src-tauri/src/windows.rs` show/hide logic just works there. Document GNOME's degraded fallback explicitly once confirmed.
